# DECISIONS — 02-01 model-bench

## D-1. 받은 모델 전부를 측정하고, 그 결과로 이후 사용 모델을 고른다

- **선택:** Ollama에 받아 둔 모델 전부를 측정 대상으로 한다. 측정 결과로 이후 연습에서 쓸 모델을 선정한다. VRAM을 넘는 MoE 모델 `qwen3:30b`는 반드시 포함한다(`docs/DECISIONS.md` R-11).
- **근거:** 이 연습의 목적이 "이 PC에서 어떤 모델이 쓸 만한지 숫자로 아는 것"이다(BRIEF 2절). 사용자가 받은 모델 전부를 평가해 이후 사용 모델을 선정하기로 했다(2026-10-05).
- **배제한 대안:**
  - GPU에 다 들어가는 모델만 측정 — 저장소 R-11이 이미 배제했다. VRAM을 넘는 모델이 쓸 만한지 알 수 없게 된다.
  - 이후 연습에서 쓸 모델만 골라 측정 — 사용 모델을 고르는 것이 이 측정의 결과여야 하는데 측정 전에 정하게 된다. (에이전트가 적은 사유이며 사용자 확인 전)

## D-2. `num_ctx`는 4096으로 고정한다

- **선택:** 모든 모델을 `num_ctx` 4096으로 측정한다.
- **근거:** 모델마다 컨텍스트가 다르면 KV cache 크기가 달라져 VRAM·속도 비교에 조건 차이가 섞인다. 4096으로 통일해 비교 조건을 맞춘다(연습 플랜 2절). 사용자가 4096 고정을 택했다(2026-10-05).
- **배제한 대안:**
  - 모델마다 다른 `num_ctx`(모델 기본값 등) — 비교 조건이 달라진다. (에이전트가 적은 사유이며 사용자 확인 전)

## D-3. `/api/generate`(`stream: false`) 응답 필드와 nvidia-smi·`/api/ps`로 측정한다

- **선택:** `/api/generate`를 `stream: false`로 호출해 응답의 `eval_count`·`eval_duration`·`prompt_eval_*`·`load_duration`으로 속도와 로드 시간을 얻는다. VRAM은 nvidia-smi로 샘플링하고, GPU/CPU 비율(PROCESSOR)은 `/api/ps`로 얻는다. 사용자가 이 방식을 택했다(2026-10-05).
- **근거:** 속도 수치를 Ollama가 응답에 담아 주는 값에서 바로 읽을 수 있고, 클라이언트 쪽 시간 측정이 섞이지 않는다(연습 플랜 1·2절).
- **배제한 대안:**
  - 스트리밍으로 호출해 클라이언트에서 시간 측정 — 네트워크·파싱 시간이 섞인다. (에이전트가 적은 사유이며 사용자 확인 전)
  - `ollama ps`·`ollama run --verbose` 출력 파싱 — 텍스트 출력 형식에 의존한다. (에이전트가 적은 사유이며 사용자 확인 전)

## D-4. 프롬프트 3개 × 반복 3회로 재고, 첫 실행값은 따로 표시해 평균에서 뺀다

- **선택:** 모델마다 프롬프트 3개 × 반복 3회를 실행한다. 모델의 첫 실행값(디스크 로드, PTX JIT)은 따로 표시하고 평균·표준편차에서 뺀다. 사용자가 이 조건을 택했다(2026-10-05).
- **근거:** 반복해야 평균과 편차를 낼 수 있다(연습 플랜 1절). 첫 실행은 디스크 로드와 PTX JIT가 섞여 이후 실행과 다른 값이므로 섞으면 평균이 흐려진다(연습 플랜 4절).
- **배제한 대안:**
  - 첫 실행값을 평균에 포함 — 로드 시간이 섞여 속도 평균이 왜곡된다. (에이전트가 적은 사유이며 사용자 확인 전)
  - 첫 실행값을 버리고 기록하지 않기 — 콜드 로드 시간도 이 PC에서 모델을 쓸 때 겪는 값이다. (에이전트가 적은 사유이며 사용자 확인 전)

## D-5. 모델이 바뀔 때마다 이전 모델을 `keep_alive: 0`으로 내린다

- **선택:** 다음 모델을 측정하기 전에 이전 모델을 `keep_alive: 0`으로 바로 내린다. 사용자가 규칙대로 하고 결정으로 따로 남기기로 했다(2026-10-05).
- **근거:** 저장소 규칙(`CLAUDE.md`)이다. 두 모델이 VRAM에 겹치면 11GB를 넘길 수 있고(01-01-local-chat v0.1 D-6), 겹치면 VRAM·속도 측정값이 오염된다(연습 플랜 4절). 이전 모델이 남아 있지 않아야 모델마다 콜드 로드 시간을 잴 수 있다.
- **배제한 대안:**
  - Ollama 기본 `keep_alive`(5분)에 맡기기 — 이전 모델이 VRAM에 남아 다음 모델과 겹친다. (에이전트가 적은 사유이며 사용자 확인 전)

## D-6. 결과 표는 pywebview 화면에 보여 준다

- **선택:** 모델별 tok/s와 VRAM 표를 pywebview 화면에 보여 준다. 사용자가 이 방식을 택했다(2026-10-05).
- **근거:** 저장소 기술 기준이 화면이 있는 연습은 Python + pywebview로 정한다(`AGENTS.md`, `docs/DECISIONS.md` R-9). 사용자가 화면 표시를 택했다.
- **배제한 대안:**
  - 표를 CLI(터미널) 출력과 CSV로만 내고 화면을 만들지 않기 — 사용자가 화면에 보여 주는 쪽을 택했다. (에이전트가 적은 사유이며 사용자 확인 전)

## D-7. 표와 함께 Plotly 차트를 화면에 보여 준다

- **선택:** D-6의 표와 함께 측정 결과를 Plotly.js 차트로 화면에 보여 준다. 사용자가 차트 표시를 택했다(2026-10-05).
- **근거:** 모델 사이 tok/s·VRAM 차이는 숫자 표보다 차트로 한눈에 비교된다. 저장소 기술 기준이 차트에는 Plotly.js를 쓴다(`docs/refs/03-project-list.md` 2절).
- **배제한 대안:**
  - 표만 보여 주기(BRIEF 완료 조건 그대로) — 사용자가 차트 표시를 택했다. (에이전트가 적은 사유이며 사용자 확인 전)

## D-8. 측정 결과를 CSV로 저장하되, 날짜별 누적은 이번 버전에서 뺀다

- **선택:** 측정 결과를 CSV 파일로 저장한다. 실행할 때마다 날짜별로 쌓거나 두 날짜 결과를 겹쳐 보는 기능은 이번 버전에서 만들지 않는다. 사용자가 CSV 저장을 하기로 했고(2026-10-05) 누적은 앞서 뺐다.
- **근거:** 앱을 닫아도 측정 수치가 파일로 남아야 이후 연습이 모델을 고를 때 근거로 쓸 수 있다. 이번 버전의 목적은 이 PC에서 어떤 모델이 쓸 만한지 숫자로 아는 것이다(BRIEF 2절).
- **배제한 대안:**
  - 저장 없이 화면 표시만 — 앱을 닫으면 측정 결과가 사라진다. (에이전트가 적은 사유이며 사용자 확인 전)
  - 연습 플랜 Phase 3대로 날짜별 CSV 누적과 두 날짜 겹쳐 보기 — 사용자가 누적을 이번 버전에서 뺐다. (에이전트가 적은 사유이며 사용자 확인 전)

## D-9. 화면에 "측정 실행" 버튼을 둔다

- **선택:** pywebview 창에서도 측정을 시작할 수 있는 "측정 실행" 버튼을 둔다. 버튼은 CLI와 같은 측정(`run_bench`)을 돌려 CSV를 저장하고 결과를 갱신한다. 사용자가 버튼을 두기로 했다(2026-10-05).
- **근거:** 창 하나에서 측정과 결과 확인을 이어서 할 수 있다. 측정 로직은 CLI와 같아 중복이 없다.
- **배제한 대안:**
  - 버튼을 빼고 창은 결과를 보여 주기만 하기(측정은 CLI로만, PLAN의 Phase 2 범위 그대로) — 사용자가 버튼을 두는 쪽을 택했다. (에이전트가 적은 사유이며 사용자 확인 전)

## D-10. 측정 호출은 `num_predict` 256, `temperature` 0, `seed` 0으로 고정한다

- **선택:** 모든 측정 호출에 `num_predict` 256(응답을 256토큰에서 자른다), `temperature` 0, `seed` 0을 쓴다. 사용자가 구현에서 쓴 이 값 그대로 기록하기로 했다(2026-10-05).
- **근거:** 한 호출이 길어지지 않게 해 모델 6개 × 9호출 측정이 15분 안팎에 끝나게 한다. 모든 모델에 같은 상한과 같은 샘플링 조건을 줘 비교 조건을 통일한다(D-2와 같은 이유). `qwen3`처럼 사고 과정이 긴 모델은 답을 끝내지 못한 채 잘릴 수 있지만 tok/s는 같은 조건으로 비교된다.
- **배제한 대안:**
  - `num_predict` 제한 없이 끝까지 생성 — 사고 과정이 긴 모델이 호출 하나에 수 분 걸려 측정 시간이 크게 늘 수 있다. (에이전트가 적은 사유이며 사용자 확인 전)
  - 모델 기본 샘플링(`temperature`·`seed`)을 그대로 사용 — 호출마다 출력 길이가 달라져 비교 조건이 흔들린다. (에이전트가 적은 사유이며 사용자 확인 전)

## D-11. 생성 능력이 없는 모델(임베딩 모델)은 측정에서 건너뛴다

- **선택:** `/api/show`의 `capabilities`에 `completion`이 없는 모델(예: `bge-m3`)은 측정하지 않고 건너뛴 모델로 출력한다. D-1의 "받은 모델 전부"에 대한 예외다. 사용자가 이 방식으로 기록하기로 했다(2026-10-05).
- **근거:** 임베딩 모델은 `/api/generate`로 텍스트를 생성할 수 없어 이 연습의 측정값(tok/s)을 낼 수 없다. 측정하려 하면 오류만 남는다.
- **배제한 대안:**
  - 임베딩 모델도 측정 대상에 넣고 오류 행으로 남기기 — 의미 없는 오류 행이 CSV에 섞이고 표·차트에 빈 모델이 생긴다. (에이전트가 적은 사유이며 사용자 확인 전)
  - 임베딩 모델은 별도로 임베딩 속도를 측정 — 이번 버전 범위(BRIEF 2절: 속도·VRAM 실측)를 넘고 측정 코드가 더 필요하다. (에이전트가 적은 사유이며 사용자 확인 전)
