# 02-02 ctx-scaling — 컨텍스트 길이에 따른 VRAM·속도 한계

## 1. 개요

`num_ctx`를 2K → 4K → 8K → 16K → 32K로 늘려 가며 모델별 VRAM 사용량, 생성 속도, GPU 적재
비율이 어떻게 변하는지 재는 CLI다. "이 모델은 이 PC에서 컨텍스트를 어디까지 쓸 수 있나"를 숫자로 정한다.
결과는 Plotly HTML 파일 하나로 낸다.

- KV cache가 컨텍스트 길이에 비례해 커지는 것 확인
- GPU 적재가 깨지는 지점(100% GPU → CPU 혼합) 찾기
- 긴 프롬프트의 프롬프트 처리 속도 측정

## 2. 기술 스택

| 항목 | 내용 |
| --- | --- |
| 런타임 | Python CLI + Plotly 정적 HTML |
| 언어·패키지 | Python 3.13(uv), `ollama`, `numpy`, `plotly` |
| Ollama API | `/api/generate`(options.num_ctx), `/api/ps` |
| 모델 | `qwen3:8b`, `exaone3.5:7.8b`, `gemma3:12b` |
| num_ctx | 2048·4096·8192·16384·32768(측정 변수) |

## 3. 간단한 플랜

| Phase | 목적 | 완료 조건 |
| --- | --- | --- |
| 1 | 측정 | 모델 × num_ctx 5단계 결과 CSV에 VRAM_MiB·PROCESSOR·tok/s 열이 채워진다 |
| 2 | 시각화 | `report.html` 하나에 모델별 "num_ctx–VRAM" 선과 9,303MiB 여유선이 그려지고, GPU 100%가 깨진 점이 다른 색으로 표시된다 |
| 3 | 권장값 | 모델별로 "100% GPU를 유지하는 최대 num_ctx"가 표로 출력된다 |

## 4. 하드웨어 메모

- 32K에서는 8B 모델도 GPU에 다 안 들어갈 수 있다. 실패가 아니라 측정 결과로 기록한다.
- 긴 프롬프트는 같은 문서를 잘라 길이만 바꿔 만든다. 프롬프트 처리 시간이 길어지므로 요청 타임아웃을 넉넉히(10분) 둔다.
- 이 결과로 `01-hardware.md` 5.2절과 각 프로젝트의 `num_ctx` 권장값을 보정한다.
