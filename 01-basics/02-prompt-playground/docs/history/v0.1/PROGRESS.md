## 계획된 작업

### Phase 1 — 변형 실행 (완료)

- **무엇을 했나:** `src/prompt_playground/`에 변형 순차 실행(`runner.py`)과 스펙 JSON → 결과 JSON CLI(`__main__.py`)를 만들었다. `pyproject.toml`·`.python-version`(3.13)·`tests/test_runner.py`를 추가했다.
- **결과:** 변형 N개(1~6개, 범위 밖이면 `ValueError`)를 하나씩 순서대로 `qwen3:4b`(`think=True`, `num_ctx` 4096)에 보내고 결과 N개를 JSON 하나로 저장한다. 변형 하나가 실패해도 나머지는 계속하고 그 결과에 `error`를 담는다.
- **검증:** `uv run pytest` 9개 통과(순서·고정 모델·`think`·옵션 4종·6개 상한·실패 격리·JSON 저장·타임아웃/연결 오류 격리). 실제 Ollama `qwen3:4b`로 변형 3개를 실행해 결과 3개가 JSON에 저장됐고 오류는 없었다. 변형 하나에 20~46초(1300~2900토큰, 대부분 사고 과정)가 걸렸다. 세션 내 리뷰어(`reviewer`)가 검증했다. 반대 벤더 검증은 R-16에 따라 하지 않는다.
- **특이사항:** 리뷰어가 "미흡 2건"으로 판정했다. (1) `httpx.ReadTimeout` 같은 httpx 예외를 잡지 않아 변형 하나의 타임아웃이 나머지를 취소하고 앞선 결과도 저장되지 않는 문제 → `httpx.HTTPError`를 변형 하나의 실패로 담도록 고치고 테스트 3개를 추가했다(`httpx`를 직접 의존에 추가). (2) `PROGRESS.md` 기록 → 이 항목으로 해결했다. 리뷰어의 재검증은 하지 않았고, 수정 후 실제 모델 재실행도 하지 않았다(바뀐 곳은 예외 처리뿐이고 단위 테스트로 확인했다).
- **관찰:** 6개를 순차 실행하면 2~4분이 걸릴 수 있어 Phase 2의 화면에는 진행 표시가 필요해 보인다. 설계 결정이 아니라 관찰이며 Phase 2에서 다시 다룬다.

### Phase 2 — 나란히 보기 (완료)

- **무엇을 했나:** `webapp.py`(pywebview 창과 `Api`: 입력 검증, 한 번에 한 실행, 작업 스레드에서 순차 실행하며 결과마다 화면에 이벤트 전달, 끝나면 `out/playground-*.json` 저장)와 `ui/index.html`(프롬프트·변형 입력 행 1~6개, 결과를 열로 표시)을 만들었다. `[project.scripts]`에 `prompt-playground`를 등록했다.
- **결과:** 변형 N개를 실행하면 결과 N개가 열로 나란히 놓이고, 열마다 파라미터 값(`temperature`·`top_p`·`seed`·시스템 프롬프트)·생성 토큰 수·소요 시간이 보인다. 사고 과정은 접이식, 실패한 변형은 그 열에 오류를 표시한다. 열은 실행 전에 먼저 만들어 결과 이벤트가 열보다 먼저 도착하는 경쟁을 피하고, 지금 실행 중인 열에 "실행 중…"을 표시한다(Phase 1 관찰의 진행 표시).
- **검증:** `uv run pytest` 22개 통과(Api 입력 거절 8종·순서·중복 실행 거절·오류 뒤 busy 해제, 실제 창 GUI 테스트 1개: 변형 3개 입력→실행→열 3개와 파라미터·`N토큰 · X초`·본문·사고 과정 확인). 실제 `qwen3:4b`로 창을 구동해 변형 2개를 실행, 열 2개에 파라미터·1824토큰 29.057초·1302토큰 19.311초가 표시되고 JSON이 저장됐다. 세션 내 리뷰어(`reviewer`)가 "통과"로 판정했다(반대 벤더 검증은 R-16에 따라 하지 않는다). 열 N개 표시, 열마다 파라미터·토큰 수·소요 시간, 중복 실행·창 닫기·입력 검증 우회·XSS·범위 초과를 점검했고 막을 결함은 없었다.
- **리뷰어의 경미한 지적:** (2) 성공인데 `eval_count`가 없으면 "null토큰"이 표시됨 → `?`로 표시하도록 고쳤다. 나머지는 고치지 않았다. (1) 실행 거절 시 다른 실행이 돌고 있어도 입력이 풀림(정상 UI로는 도달 불가, 페이지를 다시 불러온 경우만). (3) GUI 테스트가 N=3 성공 경로만 보고 실패 열·N=1·6 경계·소요 시간 숫자 여부는 DOM 수준에서 검사하지 않음. (4) `seed`에 범위 제한이 없고 소수·`True`를 조용히 받음(BRIEF 요구 밖).
- **특이사항:** 창을 만들 때 `Windows fatal exception: code 0x8001010d` 스택 덤프가 로그에 섞이지만 테스트는 통과하고 종료 코드는 0이다(WinForms COM 소음으로 보이며 원인은 확인하지 않았다). `seed 1`·`temperature 1`·`top_p 0.9` 같은 조건의 실행이 Phase 1 실행과 같은 토큰 수(1302)와 같은 문장으로 나왔다. 재현성 판단은 Phase 3·4에서 하며 여기서는 판정하지 않는다.

### Phase 3 — 재현성 표시 (완료)

- **무엇을 했나:** `repro.py`(같은 조건 판정과 글자 단위 비교)를 만들고, 결과가 나올 때마다 같은 조건의 가장 앞선 열과 비교해 화면의 열에 표시하고 저장 JSON(`results[].repro`)에도 남기게 했다. 같은 조건은 `temperature`·`top_p`·`seed`·시스템 프롬프트가 모두 같은 것이다(사용자가 정함, 2026-10-05). 답(`response`)과 사고 과정(`thinking`)을 따로 비교해 둘 다 표시한다(사용자가 정함).
- **결과:** 열에 "#1과 같은 조건 · 답 글자 단위로 같음/다름(N번째 글자부터) · 사고 과정 …"이 표시된다. 같은 조건의 앞선 열이 없으면 표시하지 않고, 오류가 난 실행이 끼면 비교하지 않고 이유를 표시한다.
- **검증:** `uv run pytest` 34개 통과(비교 로직 11개: 같음·다른 위치·접두사·조건 필드별 불일치·가장 앞선 열 기준·5개 동일 조건·오류, Api 이벤트·저장 JSON, 실제 창 GUI 테스트: 5행 시나리오에서 같은 조건은 "같음", seed가 다르면 표시 없음, 출력이 달라지는 가짜 모델은 "다름"). 실제 `qwen3:4b`로 같은 조건 2행을 창에서 실행해 표시가 나오는 것을 확인했다. 세션 내 리뷰어(`reviewer`)가 "통과"로 판정했다(반대 벤더 검증은 R-16에 따라 하지 않는다). 비교 로직 경계(접두사·빈 문자열·이모지·유니코드 정규화)와 같은 조건 판정(0.2 vs 0.20, int/float)을 직접 실행해 확인했고 범위 초과는 없었다.
- **리뷰어의 경미한 지적:** (1) 같은 조건 비교는 한 번의 실행 안의 행끼리만 되고 기본 행 둘은 `temperature`가 달라 사용자가 값을 맞춰야 한다 → 화면에 사용법 한 줄을 추가했다. (3) `test_repro.py`의 남은 빈 줄을 정리했다. 단위 테스트에 유니코드·int/float 입력 케이스가 없고 GUI 테스트가 답·사고 과정이 한쪽만 다른 혼합 경우를 보지 않는 것은 고치지 않았다(직접 실행해 확인됨). (2) 가장 앞선 같은 조건 열이 오류면 뒤의 성공한 두 열끼리는 비교되지 않는다 → 정해진 설계("가장 앞선 열")의 부산물이고 `unavailable`이 표시되므로 그대로 둔다. 참고: 모델이 lone surrogate를 내면 `save_results`가 실패할 수 있다(Phase 1 코드의 기존 문제, 이번 변경과 무관).
- **특이사항(관찰, Phase 4에서 확인할 것):** 실제 `qwen3:4b`에서 같은 조건(`temperature 0.2`·`top_p 0.9`·`seed 1`) 2행이 서로 다른 출력을 냈다(1824토큰 vs 1265토큰, 답은 5번째 글자부터, 사고 과정은 205번째 글자부터 다름). 앞선 별도 실행에서 같은 조건의 첫 요청은 둘 다 1824토큰이었다. 원인은 확인하지 않았다. 결론은 Phase 4의 5회 실행으로 낸다.

### Phase 4 — 재현성 검증 기록 (완료)

- **무엇을 했나:** 같은 조건을 5회 순차 실행하는 배치를 4개 돌렸다. 조건 P(`temperature 0`·`top_p 0.9`·`seed 1`, 02-05가 쓸 방식)와 조건 Q(`temperature 0.2`, Phase 3에서 출력이 갈린 조건)를 각각 모델이 적재된 상태(웜)와 `keep_alive: 0`으로 내린 직후(콜드)에 실행했다. 결과를 `docs/refs/seed-reproducibility.md`에 기록했다. 조건 두 가지는 BRIEF에 없어서 내가 정했다.
- **결과:** 웜에서는 P·Q 모두 5회가 답·사고 과정 모두 글자 단위로 같았다. 콜드에서는 P·Q 모두 첫 요청만 달랐고(P 1419토큰, Q 1824토큰) 이후 4회는 웜과 같았다. 콜드 첫 출력은 앞선 별도 세션들(Phase 1 CLI, Phase 2·3 실제 창)의 첫 출력과 글자 단위로 같았다. 원인은 조사하지 않았다.
- **검증:** `repro.compare_text`로 배치 안과 배치 사이, 앞선 실행과의 일치를 글자 단위로 비교했고 해시(`sha1(답+NUL+사고 과정)` 앞 8자리)를 문서 표에 남겼다. 세션 내 리뷰어(`reviewer`)가 "통과"로 판정했다(반대 벤더 검증은 R-16에 따라 하지 않는다). 표의 토큰 수·해시 20칸을 원본 JSON에서 직접 계산해 모두 일치함을, 콜드 #1이 웜과 처음 달라지는 위치와 앞선 3개 실행과의 글자 단위 일치를 확인했다. 코드 변경은 없었다.
- **리뷰어의 경미한 지적과 처리:** (1) 1절에서 "콜드 첫 출력은 항상 같다"고 한 것이 증거(P 2회·Q 3회)보다 강하고 앞선 세 실행을 콜드로 확정했다 → "관찰한 범위에서는 매번 같았다"로 낮췄다. (2) 한계에 "콜드"가 "모델 적재 직후"와 "직전에 같은 프롬프트의 요청이 없던 상태(캐시 재사용 여부)"를 분리하지 못한다는 교란 가능성이 빠져 있었다 → 4절에 추가하고 5절 표현을 맞췄다.
- **특이사항:** 원본 결과 JSON은 `out/`(`.gitignore`)에 있어 커밋되지 않는다. 문서 표의 토큰 수·해시가 증거다. 이 문서를 02-05가 읽게 하는 일(ROADMAP "착수할 때 넘길 것" 반영)은 하지 않았다. 저장소 문서라 사용자 요청이 있어야 한다.
