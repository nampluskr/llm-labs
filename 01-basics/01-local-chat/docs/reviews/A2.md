## 유효하지 않은 지적과 반박 근거

지적 자체는 맞지만 고치지 않은 것과 그 근거다. 같은 지적이 다음 Phase에서 다시 나오면 이 판정을 따른다.

- **1/3회차 #2, 2/3회차 #1·#3 (프로토콜을 어긴 입력에서의 차이).** 실제 Ollama는 통계를 정수로, 줄을 비어 있지 않은 JSON으로 보낸다. 이 입력은 SDK(`pydantic` 검증·줄 파서)와 직접 HTTP 사이의 구현 차이에서 나오고, 두 층이 같아지려면 HTTP 층이 SDK의 변환·파서를 흉내 내야 한다. HTTP 층을 일부러 엄격하게 하거나 느슨하게 만들어 맞추는 것은 비용 대비 얻는 게 없다. 확인한 것: 이런 입력에서도 **어떤 층도 예외를 밖으로 내지 않고** `Done` 또는 `Error`로 끝난다(예외 누출은 1/3회차 #1에서 고쳤다). 세 층이 다른 것은 "성공으로 볼지 오류로 볼지"뿐이다. 문자열 `content` 같은 명백한 타입 오류는 고쳤다(2/3회차 #2).
- **1/3회차 #4 (실패 시 tok/s 줄 없음).** PLAN 조항은 "토큰을 순차 출력한 **뒤** tok/s를 한 줄 출력한다"이고, 통계는 성공한 호출(`Done`)에만 있다. 실패에는 통계가 없어서 줄을 만들면 거짓 값이 된다. 대신 `[이름] 오류(kind): 메시지` 한 줄을 낸다.

## 미해결 · 남은 위험

- Critical 없음. 위 "유지" 항목 외 미해결 지적 없음.
- 검토자는 정적 검토였고 테스트를 실행하지 않았다. 구현 쪽에서 18개 테스트 통과를 확인했다.
- 막힌 `next()` 호출을 다른 스레드에서 `close()`로 중단할 수는 없다(검토자 언급). 스트림이 막혀도 읽기 타임아웃(기본 300초)이 상한이다. Phase 3에서 UI는 호출 층을 작업 스레드에서 돌리고 토큰 사이에 중단 플래그를 확인하는 방식을 써야 한다.
- UTF-8 서브프로세스 테스트는 HTTP 층으로만 돌렸다. 세 층 모두의 한글 출력은 실서버 수동 실행으로 확인했다.
- 적대적 검증 3회 중 2회 사용.
