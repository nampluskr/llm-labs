- **결과:** 노트북 3개(실행 결과 출력 포함). 이 연습의 uv 환경도 만들었다(`pyproject.toml`, `uv.lock`, `.python-version` 3.13; `ollama`·`langchain-ollama`·`httpx`·`pywebview`·`jupyter`·`ipykernel`).

- **특이사항:**
  - `langchain-ollama`의 `stream()`은 통계가 든 청크(`done=True`) 뒤에 내용 없는 청크를 하나 더 낸다. 그래서 "마지막 청크"가 아니라 `done`이 참인 청크에서 통계를 읽는다.
  - 청크 수(76·69·71)가 생성 토큰 수(78~90)보다 작다. 청크 하나가 항상 토큰 하나는 아니다. 노트북은 청크를 그대로 출력한다.
  - 03의 "첫 토큰까지" 2.09s는 모델 적재 시간이 섞인 값이다(01·02는 0.05s, 이미 적재된 상태).
  - 노트북은 `THINK=False`로 고정했다. 사고 과정 표시는 아직 미정이다(Phase 3 전에 정한다).

### Phase 2 — 공통 호출 층 (2026-10-04) — 완료

- **무엇을:** `src/local_chat/clients/`에 호출 층 3개(`ollama_client.py`·`langchain_client.py`·`http_client.py`)와 공유 이벤트(`events.py`)를 만들었다. 모두 `stream(messages, *, model, options)` 제너레이터이고 `Token`을 0개 이상, 마지막에 `Done`(통계) 또는 `Error`(kind: connection·model_not_found·other)를 정확히 하나 낸다. 도중에 `close()`하면 연결이 닫히고 마지막 이벤트 없이 끝난다. 콘솔 진입점 `python -m local_chat.console`이 세 방식을 차례로 돌려 토큰을 순차 출력하고 tok/s를 한 줄 출력한다.
- **결과:** `src/local_chat/`(패키지, uv_build)와 `tests/test_clients.py`. `pyproject.toml`에 pytest와 빌드 설정을 추가했다.
- **검증:**
  - 실제 Ollama(`qwen3:8b`)로 `python -m local_chat.console --client all`을 실행했다. 세 방식 모두 한글 토큰을 순차 출력하고 `[이름] N토큰 | 44.x tok/s`를 한 줄 출력했다.
  - 가짜 Ollama 서버 테스트 통과(최종 18개; 아래 적대적 검증 보완 포함). 처음 12개: 같은 입력에 세 층이 같은 이벤트, 요청 본문(모델·옵션·메시지·think=False) 동일, done 뒤 빈 청크, 모델 없음, 서버 없음, 스트림 도중 오류줄, done 없이 끊김, 해석 불가 줄, 통계 없는 done, 중단 시 서버가 연결 끊김을 봄, 콘솔 출력·종료 코드.
- **특이사항:**
  - 테스트가 불일치 하나를 잡았다. 통계가 없는 `done` 청크를 http는 오류로 처리했는데 ollama·langchain은 `Done(None, None)`을 냈다. 공통 `make_done`으로 검증해 세 층이 모두 `Error`를 내게 고쳤다.
  - 콘솔 `run()`의 `out=sys.stdout` 기본값이 import 시점에 고정돼 출력 캡처가 안 되던 것을 `None` → 호출 시점 `sys.stdout`으로 고쳤다.
  - 한글 인코딩(Phase 2 콘솔): 진입점에서 stdout을 UTF-8로 맞춘다. HTTP는 응답을 UTF-8로 해석한다. 테스트에 한글·이모지 토큰을 넣었다.
  - 이 환경의 `uv run pytest`는 rtk가 출력을 줄여 "No tests collected"로 보인다. `rtk proxy uv run python -m pytest tests`로 원본 출력을 확인했다.
- **적대적 검증:** 필수 통과 Phase. 세션 내 리뷰어(Critical·Major 없음, Minor 4건 모두 반영) → Codex `gpt-6.1-sol` 2회(2/3). 기록은 `docs/reviews/A2.md`.
  - Critical 없음. Major 3·Minor 2(1회차)와 Major 2·Minor 2(2회차) 중 오류 본문의 비문자열 `error`(예외 누출), SDK 층 읽기 타임아웃 없음, 비문자열 `content`, 콘솔 인코딩·flush 테스트 공백, 테스트 멈춤 가능성을 고쳤다.
  - 고치지 않은 것: 프로토콜을 어긴 응답(통계가 문자열, 빈 줄)에서 SDK와 HTTP의 성공/오류 판정이 다른 점, 실패 시 tok/s 줄 없음. 근거는 A2의 "유효하지 않은 지적과 반박 근거".
  - 알려진 한계: 막힌 `next()`는 다른 스레드의 `close()`로 못 끊는다(읽기 타임아웃 300초가 상한). Phase 3 UI는 작업 스레드 + 중단 플래그를 써야 한다.
  - 검증 도중 호출 층에 `read_timeout` 인자(기본 300초)가 생겼다. Phase 2 완료 조건에는 없던 것이지만 세 층의 종료 동등성을 위해 필요했다.

### Phase 3 — 채팅 화면(앱 3개) (2026-10-04) — 완료

- **무엇을:** pywebview 화면 하나(`ui/index.html`)와 화면과 분리된 대화 세션(`session.py`)을 만들고, 호출 층마다 앱 진입점을 만들었다(`app_ollama.py`·`app_langchain.py`·`app_http.py`, `webapp.py`가 공통). 실행은 `uv run local-chat-ollama`·`local-chat-langchain`·`local-chat-http`(또는 `python -m local_chat.app_*`). 세션은 작업 스레드에서 호출 층을 돌려 토큰을 `evaluate_js`로 화면에 밀어 넣고, 질문마다 시스템 + 직전 10턴(질문·답 쌍) + 새 질문을 보낸다. 답변 중 다시 질문하면 거절하고(보내기 버튼도 막힘), 중단 버튼과 창 닫기는 스트리밍을 멈춘다.
- **결과:** `src/local_chat/{session,webapp,defaults,app_*}.py`, `src/local_chat/ui/index.html`, `tests/{test_session,test_gui}.py`·`gui_driver.py`·`fake_ollama.py`·`conftest.py`. 기본값(`defaults.py`)을 콘솔과 앱이 같이 쓴다.
- **검증:**
  - 테스트 64개 통과(호출 층 18, 세션 22, 실제 pywebview 창 24 = 앱 3개 × 8 시나리오). 세션 테스트는 12턴 뒤 요청에 직전 10턴만 실리는지(대역과 실제 호출 층 3개 모두 가짜 서버로), 이벤트 순서, 중복 질문 거절, 중단(서버가 막힌 상태 포함), 오류 처리, emit 실패(창 닫힘)를 확인한다.
  - GUI 테스트는 앱 3개 각각 실제 창을 띄워 `evaluate_js`로 확인한다: 답변 글자 수가 단계적으로 늘고 끝나면 `N토큰 · X tok/s`와 입력이 돌아오는지, 두 번째 요청에 첫 턴이 문맥으로 실렸는지, 모델 없음 오류 표시와 재질문, 서버가 멈춰도 중단 버튼이 3초 안에 듣고 다음 질문이 나가는지, 12번 이어 질문하면 마지막 요청에 직전 10턴만 실리는지, 모델 출력의 HTML이 글자 그대로 보이는지.
  - 실제 Ollama(`qwen3:8b`)로 앱 3개를 같은 방식으로 구동했다. 세 앱 모두 두 질문에 응답이 단계적으로 표시됐고 44~47 tok/s가 표시됐다.
- **특이사항:**
  - 테스트가 경합 하나를 잡았다. 종료 이벤트를 받은 직후 다음 질문을 보내면 `join()`이 아직 시작하지 않은 스레드를 기다렸다. `join`을 "종료 이벤트 emit까지 끝난 상태" 이벤트 기준으로 바꾸고, 종료 이벤트 emit 전에 기록 갱신과 busy 해제를 끝내게 했다.
  - 화면 표시의 `2.0 tok/s`가 JS에서 `2`로 나오던 것을 `toFixed(1)`로 고쳤다.
  - 정한 동작(PLAN에 없던 세부): 답변 중 새 질문은 거절한다(중단하고 보내기는 하지 않음). 실패한 턴은 문맥에 남기지 않고, 사용자가 중단한 턴은 받은 데까지 남긴다(받은 게 없으면 남기지 않음). 모델 출력은 `textContent`로만 넣어 HTML로 해석하지 않는다.
- **세션 내 리뷰어 지적과 처리:** 완료 조건 충족, Critical 없음, Major 1·Minor 3.
  - Major — 중단 버튼이 호출 층의 막힌 읽기를 못 끊어 화면이 최대 300초 busy로 남음. **수정.** `stop()`이 직접 기록을 확정하고 `stopped`를 즉시 emit하며, 그 턴의 작업 스레드는 취소 표시가 붙어 뒤에서 정리만 한다(이후 이벤트 버림, emit 직렬화로 `stopped` 뒤에 토큰이 끼지 않음). 막힌 스레드가 남아 있어도 새 질문을 받는다.
  - Minor — `gui_driver`의 죽은 `scenario` 인자와 항상 참인 `user_html_escaped`. **수정.** 시나리오(ok·stop·many·escape)로 실제 사용하고, HTML 이스케이프를 실제로 검증한다.
  - Minor — GUI 테스트에 중단 버튼·11턴 이상 시나리오 없음. **수정.** 위 시나리오로 추가했다.
  - Minor — `tests/` 아래 `.pyc`. 저장소 `.gitignore`가 무시하므로 처리하지 않았다.
  - 범위 초과 지적(중단 버튼, `--host`·`--model` 인자, 헤더의 `num_ctx`·`temperature` 표시): 중단은 "답변 중 다시 질문"과 창 닫기 정리를 위한 것이고, `--host`는 가짜 서버로 시험하는 데 필요하며, 헤더 표시는 읽기 전용이다. 모델 전환·옵션 조절·저장은 만들지 않았다(Phase 4·5).
- **Codex 1회차(1/3) — Critical 없음, Major 4. 모두 수정:**
  - 중단 시 화면에 안 나간 토큰이 문맥에 남음(토큰 append와 전달이 원자적이지 않음) → 답을 emit이 성공한 토큰만 쌓고, 토큰 emit·기록 확정·종료 emit을 `_emit_lock` 안에서 처리했다.
  - 이전 턴의 종료 이벤트보다 새 턴의 토큰이 먼저 나갈 수 있음(확정과 종료 emit 사이의 틈) → 확정과 종료 emit을 같은 락 구간으로 묶었다. emit 중에도 busy는 풀려 있어 종료 이벤트 처리 안에서 바로 다음 질문을 보낼 수 있다.
  - 브리지 준비 전 전송 시 UI가 막힌 채 남음 → 브리지가 준비되기 전에는 보내기를 막고(버튼 비활성, 안내 문구), 브리지 호출이 실패하거나 거부되면 말풍선과 입력을 되돌린다.
  - GUI 중단 테스트가 다음 답이 오류여도 통과함(가짜 서버가 한 응답에 헤더를 두 번 써서 본문이 깨짐) → 가짜 서버에 `send_headers`·`send_body`를 분리해 고치고, 다음 답이 `1토큰 · 1.0 tok/s`로 성공하는지 단언한다.
  - 새 테스트가 실제로 결함을 잡는지 확인했다. 락 대용 `SleepyLock`으로 경합 구간을 벌려, (1) 토큰을 락 밖에서 답에 먼저 쌓거나 (2) 확정을 종료 emit 락 밖으로 빼면 각각 해당 테스트가 실패함을 확인하고 복원했다. 처음 만든 테스트는 변이를 못 잡아서(경합 구간이 너무 좁음) 이 방식으로 바꿨다.
- **Codex 2회차(2/3) — Critical 없음, Major 1·Minor 3. 모두 수정** (1회차 Major 4는 다시 나오지 않아 해소 확인):
  - Major — 이전 질문의 늦게 온 전송 거부가 다음 질문의 말풍선을 지움 → 전송마다 번호를 붙여, 자기 턴이 아직 진행 중일 때만 되돌린다.
  - Minor — 초기화 겹침(`pywebviewready` + 직접 `init()`)으로 답변 중 보내기가 열림 → 한 번만 초기화. Minor — emit 콜백 안 `stop()`이 방금 전달한 토큰을 문맥에서 뺌 → 먼저 쌓고 emit 실패 시에만 되돌림. Minor — 앱 진입점·취소된 요청의 늦은 이벤트·늦은 거부 테스트 공백 → 진입점 `app_*.main(argv)`로 창을 띄우는 시나리오, 취소된 요청이 뒤늦게 보낸 토큰이 창에 안 나오는지 관찰, 늦은 거부 시나리오 추가.
  - 변이 확인: JS 번호 가드를 빼면 늦은 거부 테스트가 실패하고 복원하면 통과한다.
  - 기록은 `docs/reviews/A3.md`. 적대적 검증 3회 중 2회 사용. 마지막 보완은 Codex로 다시 검증하지 않았다(Critical이 없어 규칙상 필수는 아님).
- **발견 — `qwen3:4b`는 `think=False`가 통하지 않는다:** 실제 Ollama로 앱을 `qwen3:4b`로 구동하다 확인했다. 인사 한마디에 500~1300토큰이 나오고 답에 `Okay, the user said ...` 같은 추론 과정이 영어 평문으로 섞인다(`thinking` 필드는 비어 있음, 00-01에서 `1+1`에 401토큰이 나온 것과 같은 현상). `qwen3:8b`는 12토큰 안팎으로 정상이다. D-4(`qwen3:4b`로 바꿀 수 있게 한다)와 D-10(사고 과정을 끈다)의 가정이 `qwen3:4b`에서는 성립하지 않는다. 사용자가 사고 과정을 표시하기로 정해 해소했다(아래 "사고 과정 표시" 항목, D-10 변경).
- **실제 Ollama 확인(최종 코드):** 앱 3개를 진입점(`app_*.main`)으로 띄워 실제 Ollama로 질문 두 개씩 구동했다. 세 앱 모두 답이 단계적으로 표시되고 61~65 tok/s가 표시됐다(`--model qwen3:4b`로 구동해 답이 길었다).

### Phase 4 — 모델 전환·옵션 (2026-10-04) — 구현 완료, 적대적 검증 대기

- **무엇을:** 화면에 모델 드롭다운과 `num_ctx`·`temperature` 입력을 더했다. 모델 목록은 `/api/tags` 전체이고(`models.py`의 `list_models`), 모델을 바꾸면 이전 모델에 빈 `messages`와 `keep_alive: 0`을 보내 바로 내린다(`unload_model`, D-6). 옵션은 `options.py`가 검증한다(`num_ctx` 정수 4096~8192, `temperature` 0~2). 세션은 `configure()`로 다음 질문부터 쓸 모델·옵션·`think`를 바꾸고, 질문을 보내는 순간의 값이 그 턴에 고정된다. 모델을 바꾸면 사고 과정 지원 여부(`think`)도 그 모델에 맞게 바뀐다(D-10).
- **결과:** `src/local_chat/{models,options}.py`, `capabilities.py`(전체 시간·크기 상한이 있는 `fetch_json`, `show_capabilities`로 정리), `session.py`(`configure`, 턴별 설정 고정), `webapp.py`(`Api.models`·`set_model`·`set_options`), `ui/index.html`(설정 줄과 잠금), 테스트 `test_{options,models,api}.py`와 GUI 시나리오 `models`.
- **검증:**
  - 실제 Ollama로 확인: `qwen3:8b`를 올려 둔 채 앱(http)에서 `exaone3.5:7.8b`로 전환하니 앱 종료 후 `/api/ps`에 `exaone`만 남았다(이전 모델이 내려감). 드롭다운에 `/api/tags`의 7개 모델이 모두 보이고 임베딩 모델 `bge-m3`만 선택 불가였다. 옵션 변경(`8192`·`0.2`)이 헤더에 반영되고 질문에 답했으며(49.2 tok/s), 범위 밖 `num_ctx`(9000)와 빈 `temperature`는 거절되고 입력이 되돌아갔고, 답변 중에는 모델·옵션 입력이 잠겼다.
  - 테스트 153개 통과(호출 층 22, 세션 30, 능력 확인 6, 모델 6, 옵션 23, Api 27, 창 39). 세 앱(`ollama`·`langchain`·`http`) 각각에서: 드롭다운 목록, 전환 시 이전 모델 `keep_alive: 0`, 전환 뒤 다음 질문의 모델·`think`, 같은 모델 선택 시 아무것도 내리지 않음, 목록에 없거나 채팅 불가 모델 거절, 답변 중 전환·옵션 변경 거절(이전 모델도 내리지 않음), 내리기 실패 시 전환 유지, `num_ctx`·`temperature`가 요청에 실림, 범위 밖·잘못된 형식 거절 후 기존 값 유지, 목록을 못 받을 때 현재 모델만 보임. 실제 창으로 위 전체 흐름을 확인한다.
  - 변이 확인: 이전 모델을 내리지 않게 하거나, 답변 중 입력 잠금을 풀거나, `num_ctx` 범위를 넓히면 해당 테스트가 실패함을 확인하고 복원했다.
- **특이사항(PLAN에 없던 세부, 정한 동작):**
  - 임베딩 전용 모델(`/api/show`의 `capabilities`에 `completion` 없음)은 드롭다운에 보이되 선택할 수 없다(채팅 불가 표시). 완료 조건 "`/api/tags`의 모델이 드롭다운에 모두 보인다"를 지키면서 400이 나는 선택을 막기 위해서다.
  - 범위 밖 값은 고쳐서 받지 않고 거절한다(입력을 이전 값으로 되돌리고 이유를 보인다). `temperature` 범위(0~2)는 PLAN에 없어 정했다.
  - 답변 중에는 모델 전환·옵션 변경을 거절한다. 전환 중(이전 모델 내리기, 최대 10초)에는 화면의 보내기와 설정 입력이 잠긴다. 이전 모델 내리기가 실패해도 전환은 유지하고 알린다.
  - 대화(문맥)는 모델을 바꿔도 이어진다. 모델 목록은 창을 열 때 한 번 읽는다(새로 받은 모델은 앱을 다시 열어야 보인다 — 모델 받기는 01-03).
  - 창을 연 시점에 `/api/tags`와 모델별 `/api/show`를 최대 8초 안에 읽는다. 못 읽으면 현재 모델만 보이고 그대로 동작한다.
- **적대적 검증:** Phase 4는 필수 통과 Phase가 아니다. 세션 내 리뷰어 → Codex 진행 예정.

### 사고 과정 표시 — D-10 변경 (2026-10-04)

- **요청:** Phase 3 마감 보고에서 `qwen3:4b`가 `think=False`를 무시한다는 발견을 보고하자, 사용자가 "사고 과정을 표시해 주세요"라고 정했다.
- **조치:**
  - 호출 층 3개가 `Thinking` 이벤트를 낸다(`stream(..., think=False)` 인자 추가). `think=True`일 때 사고 과정이 `Thinking`, 답이 `Token`으로 분리돼 온다. 세션은 `thinking` 이벤트를 화면에 보내되 대화 기록·문맥에는 넣지 않는다.
  - 모델 지원 여부는 `/api/show`의 `capabilities`로 확인한다(`capabilities.py`의 `supports_thinking`). 지원하는 모델에만 `think=True`, 나머지는 `False`다. 실제 Ollama로 `qwen3:8b`·`qwen3:4b`는 `think=True`에서 `thinking` 필드가 분리되고, `exaone3.5:7.8b`는 `think=True`에 400을 내며 `False`는 정상임을 확인했다.
  - 화면은 답 위에 접이식 블록을 둔다. 생각하는 동안 "생각 중…"으로 펼쳐 두고, 답이 시작되면 "생각 과정"으로 접으며 사용자가 다시 펼 수 있다. 사고 과정은 텍스트 노드로 넣어 HTML로 해석하지 않는다. 헤더에 "사고 과정 표시/없음"을 보인다.
  - DECISIONS D-10을 새 선택·근거·배제한 대안으로 고쳐 썼다. 연습 플랜 5절의 미정 항목을 결정으로 바꾸고 `docs/refs/` 사본을 다시 복사했다. 노트북 세 곳의 `THINK` 주석("Phase 3 전에 정한다")을 맞췄다(노트북은 계속 사고 과정을 끈다).
- **결과:** 앱 3개가 사고 과정을 표시한다. `qwen3:4b`도 답이 영어 추론으로 오염되지 않는다(실제 Ollama로 langchain·http 앱에서 사고 과정과 짧은 답이 분리돼 나옴을 확인. ollama 앱은 `qwen3:4b`가 30초 넘게 생각해 드라이버의 관찰 시간을 넘겼고, 펼친 "생각 중…" 상태까지 확인했다).
- **검증:** 테스트 77개 통과(호출 층 21, 세션 25, 능력 확인 4, 창 27; 아래 검증 보완 후 최종 91개). 새 테스트: 세 층이 같은 `Thinking` 이벤트를 내는지, `think` 인자가 요청에 실리는지, 문자열이 아닌 `thinking`은 `Error`인지, 사고 과정이 문맥에 안 들어가는지, 사고 과정만 받고 중단하면 기록하지 않는지, `capabilities` 판정(서버 없음·이상한 값 포함), 실제 창에서 "펼침 → 접힘"과 답·사고 과정 분리·HTML 비해석·다시 펼치기, 지원하지 않는 모델에 `think=False`를 보내는지. 테스트가 `capabilities`가 문자열 `"thinking"`일 때 부분 문자열로 참이 되는 허점을 잡아 고쳤다.
- **특이사항:** 사고 과정이 길다(`qwen3:4b`는 인사에 수백~천 토큰). 대화 저장(Phase 5)은 `messages`(role·content)만 저장하므로 사고 과정은 저장되지 않는다.
- **적대적 검증(사고 과정 변경):** 기록은 `docs/reviews/A3.md`의 "사고 과정 표시 변경" 절.

  - 변이 확인: JS의 접기 조건을 예전대로 되돌리면, `_abort` 호출을 빼면 해당 테스트가 실패함을 확인하고 복원했다.
