# PROMPTS — 단계별 프롬프트 예제

**사람이 복사해서 쓰는 문서다.**

지시를 매번 새로 짜지 않는다. 무엇을 만들지와 완료 조건은 이미 문서에 있으므로,
지시는 "이걸 읽고 진행해줘" 한 줄이면 된다.

아래에서 `d:/tools/project-workflow`는 가이드 레포를 클론한 경로다.
본인 경로로 바꿔 쓴다.

> **[llm-labs]** 이 사본에서는 다음처럼 바꿔 읽는다.
>
> | 원문 | llm-labs |
> | --- | --- |
> | `d:/tools/project-workflow` | `workflow` (저장소 루트 기준 상대 경로) |
> | "이 프로젝트" | "`NN-category/NN-name` 연습" — 대상 연습 폴더를 꼭 적는다 |
> | `INTENT.md` (`docs/current/`) | 저장소 `docs/INTENT.md` (모든 연습 공유) |
> | 문서를 "루트에" 둔다 | 문서를 **연습 폴더에** 둔다 |
>
> 3·7·8절에는 llm-labs용 예시를 따로 붙였다.

## 1. `INTENT.md`를 쓸 때 — `v0.1` 기획

가장 먼저 쓴다. 이 프로젝트가 무엇을 왜 하는가 — SSOT다. **에이전트가 대신 쓰게
하지 않는다. 묻게 한다.**

```
d:/tools/project-workflow/docs/DOC-SCHEMA.md 2절을 읽고,
내가 INTENT.md를 쓸 수 있게 질문만 해줘.

규칙:
- 내 답을 대신 지어내지 마
- 한 번에 하나씩 물어
- 내가 모호하게 답하면 다시 물어
- 다 끝나면 내가 말한 것만으로 초안을 만들어. 없는 내용을 채우지 마
```

INTENT는 기술·설계·수치를 담지 않는다. 무엇을·왜·변하지 않는 원칙·다루지 않는 것,
넷만 담는다.

---

## 2. 버전 문서를 쓸 때

**에이전트가 대신 쓰게 하지 않는다.** 빈칸을 채워 달라고 하지 말고, **묻게 한다.**

(무엇이 허용되는지는 `DOC-SCHEMA.md` 1절 참조 — 요청받아 질문하고 초안을 쓰는 것은
된다. 스스로 판단해서 쓰는 것이 안 된다.)

```
d:/tools/project-workflow/docs/DOC-SCHEMA.md 3절을 읽고,
내가 BRIEF.md를 쓸 수 있게 질문만 해줘.
내용이 INTENT.md에 어긋나면 그것도 지적해줘.

규칙:
- 내 답을 대신 지어내지 마
- 한 번에 하나씩 물어
- 내가 모호하게 답하면 다시 물어
- 다 끝나면 내가 말한 것만으로 초안을 만들어. 없는 내용을 채우지 마
```

`SPEC.md`, `PLAN.md`도 절 번호만 바꿔 같은 방식으로 쓴다 — 5절, 6절.
요구가 단순하면 `SPEC`을 생략하고 `BRIEF`→`PLAN`으로 가도 된다. task 분해가 필요
없으면 `backlog` 없이 `PLAN`만으로 진행한다.

**다 썼는지 확인**

```
d:/tools/project-workflow/docs/DOC-SCHEMA.md 10절 검사 목록으로
지금 폴더의 문서를 검사해줘. 고치지는 말고 결과만 표로 보여줘.
```

## 3. 프로젝트 초기화

`INTENT.md`와 버전 문서를 폴더에 넣은 다음 — `v0.1`이면 `README.md`도 함께.
기획 때 모은 참고 자료가 있으면 `refs/` 폴더째 둔다.

```
d:/tools/project-workflow/docs/INIT.md 를 읽고 이 프로젝트를 초기화해줘.
```

**기존 프로젝트를 참고해 새로 시작할 때(모드 C)는** 무엇을 참고하는지 알려준다.

```
d:/tools/project-workflow/docs/INIT.md 를 읽고 이 프로젝트를 초기화해줘.
이건 d:/projects/old-project 를 참고해 새로 시작하는 프로젝트야(모드 C).
그 프로젝트는 읽기만 하고 고치지 마. 참고한 위치는 refs에 남겨.
```

**[llm-labs]** 연습 폴더에 `BRIEF`·`DECISIONS`·`PLAN`·`README.md`를 넣은 다음.
INTENT는 저장소 `docs/INTENT.md`를 쓰므로 넣지 않는다.

```
workflow/docs/INIT.md 를 읽고 01-basics/01-local-chat 연습을 초기화해줘.
```

```
workflow/docs/INIT.md 를 읽고 07-integration/01-transcript-polish 연습을 초기화해줘.
D:/projects/speech_transcriber 를 참고하는 연습이야(모드 C).
그 프로젝트는 읽기만 하고 고치지 마. 참고한 위치는 연습의 docs/refs에 남겨.
```

**기대 반응**

| 순서 | 무엇 |
| --- | --- |
| 1 | A(신규)/C(참조 후 신규)/B(새 버전) 중 무엇인지 판별해서 먼저 말한다 |
| 2 | 전제 확인 — backlog CLI, 문서 존재 |
| 3 | 문서 검사 결과를 표로 |
| 4 | 구조 생성(INTENT·refs 이동 포함), git, 하네스 |
| 5 | 차단 증명 결과 |
| 6 | 보고 후 **멈춤** |

**빠뜨렸을 때는 멈춰야 정상이다.** 대신 채워주면 잘못 동작한 것이다.

---

## 4. 구현 시작

초기화 보고를 확인한 뒤.

```
Phase 1의 task를 순서대로 진행해줘.
task를 닫을 때마다 PROGRESS.md에 무엇을·결과·검증을 남겨.
막히면 추측하지 말고 멈추고 물어.
```

Phase 번호만 바꿔 계속 쓴다. **한 Phase씩 준다.** 전부 맡기면 중간 검증이 사라진다.

---

## 5. Phase 검증

```
Phase 1을 닫기 전에 reviewer로 검증해줘.
PLAN.md의 완료 조건을 하나씩 대조하고, SPEC의 미구현 대상을 넘어선 게 있는지도 봐.
```

**미충족이 나오면 그게 정상이다.** 매번 전부 통과하면 완료 조건이 느슨한 것이다.

**reviewer를 통과했으면 다음은 반대 벤더다.**

```
reviewer 통과했으니 docs/ADVERSARIAL-REVIEW.md 절차로 Phase 1을 반대 벤더에 검증해줘.
구현자가 누구였는지 먼저 말하고, 그 반대 벤더 CLI로 돌려.
공격 초점은 PLAN의 "적대적 검증" 절에 적힌 것을 쓰고,
결과는 docs/reviews/A1.md에 양식대로 남겨.
```

**리팩토링을 끝냈을 때**

```
이번 건 리팩토링이니까 공격 초점을 동작 동등성으로 잡아줘.
"이 변경으로 달라지는 사용자 관측 동작을 하나라도 찾아라"로 던지고,
테스트가 덮지 않는 경로도 보게 해.
```

**CLI가 없거나 모델 접근이 막히면 멈춘다.** 기본 모델로 폴백해서 같은 벤더가
검토하면 검증한 것이 아닌데 기록에는 검증으로 남는다.

## 6. 결과물 검토와 개선 요청

전 Phase가 끝난 뒤. **여기가 버전의 절반이다.** 계획은 다 됐지만 아직 안 끝났다.

```
<무엇이 불편한지 구체적으로>

이건 backlog에 없는 계획 외 개선이야.
backlog에 task를 추가하지 말고, 고친 다음 PROGRESS.md의
"계획 외 개선"에 요청·조치·결과·검증을 남겨.
```

**직전 개선이 무엇이었는지 보고 싶을 때**

```
PROGRESS.md의 "계획 외 개선"을 요약해줘. 몇 건이고 무엇을 고쳤는지.
```

**[llm-labs]**

```
workflow/docs/VERSIONING.md 를 읽고 01-basics/01-local-chat 연습의 이 버전을 마감해줘.
버전 번호는 내가 정한다. 마감 조건 4개부터 확인하고,
```

| 무엇 | 왜 사람이 보나 |
| --- | --- |

**버전 번호는 사람이 정한다.** 에이전트가 major/minor를 스스로 올리지 않는다.

## 8. 다음 버전 착수

새 버전 문서를 루트에 놓은 다음. **`README.md`와 `INTENT.md`는 다시 안 넣는다** —
README는 루트에 남아 있고, INTENT는 `docs/current/`에 그대로 있다.

```
d:/tools/project-workflow/docs/INIT.md 를 읽고 v0.2를 시작해줘.
current의 INTENT.md는 지우지 말고,
이전 BRIEF와 대조한 요약을 먼저 보여준 다음 내 확인을 받고 진행해.
```

**[llm-labs]** 새 버전 문서를 **연습 폴더**에 놓은 다음.

```
workflow/docs/INIT.md 를 읽고 01-basics/01-local-chat 연습의 v0.2를 시작해줘.
저장소 docs/INTENT.md는 건드리지 말고,
이전 BRIEF와 대조한 요약을 먼저 보여준 다음 내 확인을 받고 진행해.
```

**대조 요약을 반드시 읽는다.** 에이전트가 이번 요구를 어떻게 이해했는지가 여기
드러난다. 어긋났으면 지금 잡는 게 가장 싸다.

**직전 버전이 뭐였는지 잊었을 때**

```
docs/history/v0.1/BRIEF.md와 PROGRESS.md 요약 구간을 읽고,
지난 버전에서 무엇을 하려 했고 무엇이 남았는지 알려줘.
```

## 9. SSOT(`INTENT`)를 바꾸고 싶을 때

INTENT는 언제든 사람의 요청으로 고칠 수 있다 — `v0.1` 이후에도 (`DOC-SCHEMA.md` 2절).
**바꾸면 영향을 받는 하위 문서가 있다.** 에이전트가 무엇을 고쳐야 하는지 먼저 식별하게 한다.

```
INTENT.md의 <무엇>을 <어떻게> 바꾸고 싶어.
바로 고치지 말고, 이 변경으로 어긋나게 되는 하위 문서
(BRIEF·DECISIONS·SPEC·PLAN·backlog)가 무엇인지 먼저 표로 보여줘.
내가 확인하면 그다음에 고치자.
```

**반대 방향 — 에이전트가 SSOT 위배를 보고했을 때.** 하위 문서를 쓰다가 INTENT에
어긋나는 것을 에이전트가 발견하면 멈추고 보고한다. 그때 사람이 판단한다.

```
INTENT를 바꿔야 하는 거면 위 방식으로 진행하고,
아니면 그 하위 문서를 INTENT에 맞게 고쳐줘. 어느 쪽인지는 내가 정한다.
```

## 10. 어긋났을 때

**요구 자체가 바뀌었을 때**

```
이 요구는 SPEC에 없어. 코드부터 고치지 말고,
SPEC.md를 어떻게 바꿔야 하는지 먼저 보여줘.
```

**에이전트가 범위를 넓혔을 때**

```
방금 만든 것 중 SPEC의 요구 ID에 대응하지 않는 게 있는지 확인해줘.
있으면 무엇이고 왜 만들었는지 설명해.
```

**hook이 이상할 때**

```
d:/tools/project-workflow/docs/HARNESS.md 5절의 차단 증명을 다시 돌려줘.
막을 것을 막는지, 통과할 것을 통과시키는지 둘 다.
```

**되돌리고 싶을 때**

```
지금까지 바뀐 것을 보여줘. 되돌리기 전에 무엇이 사라지는지 먼저 알려줘.
```

## 11. 쓰지 말아야 할 지시

| 이렇게 쓰지 않는다 | 왜 |
| --- | --- |
| "알아서 잘 만들어줘" | 완료 조건이 없으면 에이전트가 스스로 종료를 선언한다 |
| "INTENT도 네가 정해줘" | SSOT는 본인만 안다. 프로젝트의 정체성이 일반론이 된다 |
| "BRIEF도 네가 써줘" | 의도는 본인만 안다. 요구가 일반론이 된다 |
| "INTENT 어긋나도 일단 진행해" | SSOT가 흔들리면 방향이 갈라진다. 먼저 어느 쪽을 고칠지 정한다 |
| "버전 올릴 때가 된 것 같으면 네가 올려" | major/minor는 사람이 정한다 |
| "backlog에 이것도 추가해줘" | 계획과 실제가 섞인다. `PROGRESS.md`로 |
| "history에 있는 그거 좀 고쳐줘" | 기록이 사후에 바뀐다. hook이 막는다 |
| "참고 프로젝트 그거 김에 같이 고쳐줘" | 모드 C의 참조 대상은 읽기 전용이다 |
| "전 Phase 다 진행해줘" | 중간 검증이 사라진다. 한 Phase씩 |
| "그냥 넘어가고 계속해" | 멈춘 데는 이유가 있다. 무엇이 걸렸는지 먼저 본다 |
| "반대 벤더 CLI 없으니 그냥 네가 검토해" | 구현한 모델이 자기 결과를 판정하게 된다. 대체 검증안을 받고 승인부터 |
| "통과할 때까지 프롬프트 바꿔서 다시 돌려" | 3회 제한이 있다. 그 이상은 검증이 아니라 튜닝이다 |
