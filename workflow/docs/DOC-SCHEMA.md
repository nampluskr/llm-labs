# DOC-SCHEMA — 문서별 블럭 정의

`docs/current/`에 들어가는 문서가 각각 어떤 블럭으로 이뤄지는지 정의한다.

사람은 이걸 보고 쓰고, 에이전트는 이걸 보고 **검사한다.** 그래서 "잘 쓴다"가 아니라
**"있다/없다"로 판정되는 형태**로 적는다.

---

## 1. 공통 규칙

**첫 줄에 버전을 적는다.**

```
> 버전: v0.2 · 작성일: 2026-09-01
```

`docs/current/`는 폴더 이름이 버전을 말해주지 않는다. 문서가 스스로 말해야 한다.
`backlog.json`은 `meta.version`에 적는다. `INTENT.md`는 예외다 — 버전을 따라가지
않으므로 버전 줄을 강제하지 않는다 (2절).

**[llm-labs]** 버전 줄의 버전은 **그 연습의 버전**이다. 저장소 문서(`docs/INTENT.md`·
`docs/ROADMAP.md`·`docs/DECISIONS.md`)는 버전이 없으므로 `> 작성일: … · 버전 없음(저장소 전체
문서)`처럼 적는다. 저장소 `DECISIONS.md`는 4절의 형식(결정·근거·배제한 대안)을 따른다.

### 문서는 고정된 개수가 아니다

프로젝트마다 필요한 문서가 다르다. **항상 있는 것**과 **규모에 따라 있는 것**을 나눈다.

| 문서 | 언제 있나 |
| --- | --- |
| `INTENT.md` | `v0.1` 기획 때 만들고 이후 계속 있다 (2절). **[llm-labs]** 저장소 `docs/`에 하나, 모든 연습이 공유. 연습 폴더에는 없다 |
| `BRIEF.md` | 모든 버전 |
| `DECISIONS.md` | 모든 버전 |
| `PLAN.md` | 모든 버전 |
| `SPEC.md` | **선택.** 요구가 단순하면 생략하고 `BRIEF`→`PLAN`으로 간다 |
| `backlog.json` | **선택.** task 분해가 필요할 만큼 크지 않으면 `PLAN`만으로 진행한다 |
| `PROGRESS.md` | 구현이 시작되면 에이전트가 만든다 |

`SPEC`이나 `backlog`를 생략했으면, 그것을 참조하던 규칙(요구 ID 역참조, `backlog
validate`)도 그만큼 적용되지 않는다. 있는 문서에 대해서만 검사한다.

### "사람이 쓴다"는 무슨 뜻인가 — 에이전트가 할 일

문서의 **요구와 결정은 사람의 것**이다. 에이전트는 요청받아 초안을 쓰거나 고칠 수
있지만, **스스로 판단해서 내용을 만들거나 채우지 않는다.** 결과는 사람이 판단한다.

이 규칙은 자주 오해된다. "사람이 쓴다"는 말을 **"에이전트는 관여하지 않는다"** 로
읽고 손을 놓거나, 반대로 **"빈칸을 대신 채워 준다"** 로 읽고 요구를 지어내는 것
둘 다 틀렸다. 옳은 행동은 하나다 — **묻는다.**

에이전트가 문서 작성을 도울 때 지켜야 할 행동:

- **묻는다. 지어내지 않는다.** 사람이 무엇을 원하는지 모르면, 추측해서 초안에 넣지
  말고 **먼저 질문한다.**
- **한 번에 하나씩 묻는다.** 질문을 몰아서 던지지 않는다.
- **모호하면 다시 묻는다.** 사람의 답이 애매하면 그대로 받아 적지 말고 되묻는다.
- **말한 것만 적는다.** 초안에는 사람이 말한 내용만 들어간다. 빈 곳은 비운 채로
  두거나 "미정"이라고 적고, 없는 내용을 채우지 않는다.
- **손 놓지 않는다.** "이건 사람이 쓰는 문서입니다"라고 말하고 멈추는 것은 돕는
  것이 아니다. 무엇을 물어야 사람이 쓸 수 있는지 찾아서 질문하는 것이 에이전트의 일이다.

국면이 다르면 허용되는 것도 다르다.

| 국면 | 에이전트가 할 수 있는 것 |
| --- | --- |
| 작성 중 — 처음 쓰거나 버전 전환 준비 | 요청받아 질문하고, 답을 받아 초안·수정 |
| 초기화 이후 — 구현이 시작된 다음 | **손대지 않는다.** 요청 자체가 없다 |

`INTENT.md`만은 예외다. 초기화 이후에도 **사람의 요청이 있으면** 수정한다 (2절).

### SSOT 정합성 — `INTENT.md`에 어긋나지 않는다

`INTENT.md`는 이 프로젝트의 SSOT(단일 진실 원천)다. 다른 모든 문서는 INTENT에
어긋나면 안 된다. 에이전트는 문서를 쓰거나 고칠 때 항상 INTENT를 기준으로 대조한다.

두 방향의 흐름이 있다.

1. **위에서 아래로 — 사람이 INTENT를 바꿀 때.** 에이전트는 그 변경으로 영향을 받는
   하위 문서(`BRIEF`·`DECISIONS`·`SPEC`·`PLAN`·`backlog`)가 무엇인지 식별해서
   **사람에게 보고**한다. 사람이 확인하면 하위 문서를 고친다.
2. **아래에서 위로 — 하위 문서를 쓰거나 고치는 중.** 그 내용이 INTENT에 어긋나면
   에이전트는 **멈추고 사람에게 보고**한다. 사람이 검토해서, INTENT를 바꿔야 하면
   1번으로 가고, 아니면 하위 문서를 INTENT에 맞게 고친다.

**에이전트는 어긋남을 혼자 해소하지 않는다.** INTENT를 말없이 고치지도, 하위 문서를
말없이 맞추지도 않는다. 보고하고 사람의 판단을 받는다.

### 그 밖의 공통 규칙

**필수 블럭은 비워 두지 않는다.** 해당 없으면 "없음"이라고 적는다. 빈 채로 두면
빠뜨린 것인지 없는 것인지 구별되지 않는다.

**판정할 수 없는 표현을 쓰지 않는다.** "잘 동작한다", "충분히 빠르다"는 완료 조건이
아니다. "100건 처리 60초 이내", "테스트 12건 통과"처럼 기계나 사람이 명확히 판정할
수 있어야 한다.

## 2. INTENT.md

**이 프로젝트가 무엇을 왜 하는가 — SSOT.** 사람이 쓴다 (1절).

기술·설계·요구사항 ID·구현 방법·수치를 담지 않는다. 버전이 바뀌어도 변하지 않는
**의도**만 담는다. 나머지 문서가 흔들려도 이 문서가 기준점으로 남는다.

| # | 블럭 | 필수 | 담는 것 |
| --- | --- | --- | --- |
| 1 | 무엇을 하는가 | O | 이 프로젝트가 무엇을 하는 것인지. 목적 |
| 2 | 왜 하는가 | O | 이것을 원하는 이유. 무엇이 불편해서 만드는가 |
| 3 | 변하지 않는 원칙 | O | 버전이 올라가도 지켜지는 판단 기준 |
| 4 | 다루지 않는 것 | O | 이 프로젝트의 정체성 밖. 범위의 경계 |

**담지 않는 것** — 설계, 요구사항, 구현 방법, 완료 조건, 일정. 그건 버전 문서가 담는다.

### 예시

사람이 "여러 작업 폴더를 나란히 두고 각각 터미널을 띄우는 도구가 있으면 좋겠다"고
말했다고 하자. 에이전트가 2절을 읽고 질문해 받아낸 답으로 채운 INTENT는 이렇게 생긴다.

> **무엇을 하는가**
> 여러 폴더를 한 창에서 나란히 열고, 각 폴더를 작업 위치로 삼아 독립된 작업 공간으로 다룬다.
>
> **왜 하는가**
> 폴더마다 창이나 터미널을 따로 띄우면 어디가 어느 작업인지 금방 흐려진다.
> 작업 단위를 눈에 보이게 묶어두고 싶다.
>
> **변하지 않는 원칙**
> - 작업의 단위는 폴더다. 파일이 아니다.
> - 열어둔 작업 공간은 사람이 닫기 전까지 살아 있다.
> - 한 화면에서 여러 작업을 동시에 본다.
>
> **다루지 않는 것**
> - 폴더 안 파일의 편집. 이 도구는 작업 공간을 벌여놓는 것이지 편집기가 아니다.
> - 원격·클라우드 폴더.

무엇이 **안** 들어갔는지가 형식을 말해준다 — 어떤 언어로 만들지, 창을 몇 개까지 열지,
어떤 라이브러리를 쓸지가 없다. 그건 `BRIEF`·`DECISIONS`·`SPEC`이 버전마다 정한다.
INTENT는 "이 도구가 무엇이고 왜 있는가"만 붙들고, 그것은 버전이 올라가도 바뀌지 않는다.

### 수명과 취급 — 다른 문서와 다르다

| 규칙 | 내용 |
| --- | --- |
| 생성 | **`v0.1` 기획 때** 사람과 함께 가장 먼저 만든다 |
| 위치 | 항상 `docs/current/`에 상주한다. **[llm-labs]** 저장소 `docs/INTENT.md` 하나에 상주하고 모든 연습이 공유한다. 각 연습의 BRIEF·DECISIONS·PLAN은 이 INTENT에 어긋나면 안 된다 |
| 재작성 | 버전마다 새로 쓰지 않는다. 하나가 계속 이어진다 |
| 수정 | **초기화 이후에도 사람의 요청으로 언제든 수정·갱신할 수 있다** |
| history | **history로 복사하지 않는다.** 버전 스냅샷에 넣지 않는다 |
| 버전 | 버전 번호 올림과 아무 관계가 없다 (major·minor는 사람이 판단) |

**왜 history로 안 가나** — INTENT는 "지금 유효한 하나"만 의미가 있다. 과거 버전의
의도 스냅샷을 남기는 문서가 아니다. 그래서 버전 마감 시 `docs/current/`를 통째로
복사하는 규칙에서 **INTENT만 제외**한다 (`VERSIONING.md`).

**왜 버전과 무관한가** — INTENT를 고쳤다고 버전이 오르지 않는다. 반대로 버전이
올라도 INTENT를 새로 쓰지 않는다. 버전 올림은 오직 사람이 프로그램의 완성도를 보고
정한다.

## 3. BRIEF.md

**이번 버전에서 사용자가 무엇을 원하는가.** 사람이 쓴다 (1절).

`INTENT.md`가 "프로젝트가 무엇인가"라면 `BRIEF.md`는 "이번 버전에 무엇을 하는가"다.
BRIEF는 INTENT에 어긋나면 안 된다 (1절 SSOT 정합성).

| # | 블럭 | 필수 | 담는 것 |
| --- | --- | --- | --- |
| 1 | 배경 | O | 지금 어떤 상황인가. 무엇이 불편한가 |
| 2 | 이번 버전에서 풀고 싶은 문제 | O | 무엇이 해결됐으면 하는가 |
| 3 | 이전 버전에서 아쉬웠던 것 | `v0.2`+ | 무엇이 부족했는가 |
| 4 | 하지 않을 것 | O | 이번 범위 밖 |
| 5 | 완료 조건 | O | 무엇이 되면 이 버전이 끝인가 |

**담지 않는 것** — 설계, 요구사항 ID, 구현 방법, 일정.

2번과 3번은 방향이 반대다. 하나는 앞을 보고 하나는 뒤를 본다. 에이전트가 이전 버전
`BRIEF`와 대조할 때 3번이 기준이 된다.

4번이 없으면 에이전트가 범위를 스스로 넓힌다. **"없음"이라고 적는 것과 안 적는 것은
다르다.**

---

## 4. DECISIONS.md

**이번 버전에서 내린 설계 결정과 그 근거.**

결정 하나가 한 블럭이다.

| 필드 | 필수 | 담는 것 |
| --- | --- | --- |
| 번호 | O | `D-1`, `D-2` … 버전 안에서 유일 |
| 제목 | O | 무엇에 대한 결정인가 |
| 선택 | O | 무엇으로 정했나 |
| 근거 | O | 왜 그렇게 정했나 |
| 배제한 대안 | O | 무엇을 왜 안 골랐나 |

**배제한 대안이 이 문서의 핵심이다.** 없으면 같은 선택지가 다음 버전에 다시 올라온다.
검토했는데 아무것도 배제하지 않았다면 그건 결정이 아니라 기록이다.

**담지 않는 것** — 요구사항(`SPEC`), 아직 안 정한 것, 조사·실측 데이터.

버전 마감 때 각 항목을 성격에 따라 나눈다.

| 성격 | 어디로 |
| --- | --- |
| 앞으로 지켜야 할 제약 | `CLAUDE.md` · `.claude/rules/`로 승격 |
| 왜 그렇게 정했나 하는 근거 | 여기 남아 history로 |

---

## 5. SPEC.md

**이번 버전이 만족해야 할 것.** 선택 문서다 (1절) — 요구가 단순하면 생략하고
`BRIEF`의 완료 조건과 `PLAN`으로 바로 갈 수 있다.

| # | 블럭 | 필수 | 담는 것 |
| --- | --- | --- | --- |
| 1 | 기능 요구사항 | O | `FR-n` · 내용 · **판정 방법** |
| 2 | 비기능 요구사항 | O | `NFR-n` · 내용 · 판정 방법 |
| 3 | 제약사항 | O | 환경·의존·지켜야 할 한계 |
| 4 | **미구현 대상** | O | 이번 버전에서 하지 않을 것 |

ID를 붙이는 이유는 `PLAN`의 Phase와 `backlog`의 task가 역참조하기 위해서다.
ID 없는 요구는 어느 Phase가 담당하는지 추적되지 않는다.

**판정 방법이 없는 요구사항은 요구사항이 아니다.** 각 항목에 "무엇을 보면
충족됐다고 하는가"가 있어야 한다.

4번은 `BRIEF`의 "하지 않을 것"보다 구체적이다. BRIEF는 범위를 말하고 SPEC은
항목을 말한다.

**담지 않는 것** — 구현 방법, Phase 순서, 설계 결정(`DECISIONS`).

---

## 6. PLAN.md

**Phase 인덱스.** 상세 설계는 여기 쓰지 않는다.

Phase 하나가 한 블럭이다.

| 필드 | 필수 | 담는 것 |
| --- | --- | --- |
| 번호 | O | `Phase 1`, `Phase 2` … |
| 목적 | O | 한 줄 |
| 대응 요구 ID | `SPEC`이 있으면 O | `FR-1`, `NFR-2` … |
| 완료 조건 | O | 검증 가능한 형태 |

**완료 조건 없는 Phase가 하나라도 있으면 이 문서는 미완성이다.** 없으면 에이전트가
자기 판단으로 종료를 선언한다.

`SPEC`을 생략한 프로젝트에서는 대응 요구 ID 대신 `BRIEF`의 완료 조건을 가리킨다.

### 적대적 검증 절 — 필수

Phase 인덱스 끝에 **"적대적 검증"** 절을 둔다. 절차는 `ADVERSARIAL-REVIEW.md`에
있으므로 여기 옮겨 적지 않고, 이 프로젝트에서만 정해지는 두 가지만 적는다.

| 필드 | 필수 | 담는 것 |
| --- | --- | --- |
| 필수 통과 Phase | O | 미해결 Critical이 있으면 다음 Phase로 못 넘어가는 Phase 번호들 |
| Phase별 공격 초점 | O | 그 Phase에서 검토자에게 무엇을 깨라고 할 것인가. 한 줄 |

**필수 통과 Phase는 사람이 정한다.** 에이전트가 스스로 고르지 않는다.

리팩토링 Phase의 공격 초점은 항상 **동작 동등성**이다 (`ADVERSARIAL-REVIEW.md` 3절).

Phase 상세를 여기 다 쓰면 Phase 1 작업 중에도 Phase 10 내용이 컨텍스트에 로드된다.

**담지 않는 것** — task 분해(`backlog.json`), 상세 설계, 코드.

## 7. backlog.json

**작업 SSOT.** 이번 버전에 **계획한 것**의 기록이다. 선택 문서다 (1절) — task 분해가
필요할 만큼 크지 않으면 `PLAN`의 Phase만으로 진행한다.

```
meta
├── version      v0.2
└── id_seed      이전 버전의 마지막 번호 다음

task[]
├── id           프로젝트 전체에서 유일
├── phase        소속 Phase 번호
├── summary      무엇을 만드는가
├── note         이 task에서 지킬 규칙. 짧게
└── done         완료 조건
```

`note`에 설계 설명을 쓰지 않는다. backlog가 비대해지면 `list` 호출마다 컨텍스트
비용이 올라간다. 맥락은 `PLAN`과 `DECISIONS`가 담는다.

ID는 프로젝트 전체에서 유일해야 한다. 버전이 바뀌어도 번호를 다시 쓰지 않는다.
`PROGRESS.md`와 리포트가 이 번호로 역참조한다.

**진행 중에 task를 추가하지 않는다.** 계획 밖의 작업은 `PROGRESS.md`에 적는다.
여기 늘리면 "무엇을 하기로 했었나"가 사후에 바뀐다.

**검사** — `backlog validate` 통과. 완료 조건 없는 task가 없을 것.

## 8. PROGRESS.md

**실제로 한 것.** 에이전트가 진행하며 append한다. 사람이 미리 쓰지 않는다.

성격이 다른 두 구간이 있다.

| # | 블럭 | 필수 | 출처 |
| --- | --- | --- | --- |
| 1 | 계획된 작업 | O | `backlog.json`(없으면 `PLAN`) |
| 2 | 계획 외 개선 | O | 사람의 요청 |

**1. 계획된 작업** — task 완료마다 한 항목

| 필드 | 담는 것 |
| --- | --- |
| task ID | `backlog.json` 참조 |
| 무엇을 했나 | 한두 줄 |
| 결과 | 만들어진 것, 바뀐 것 |
| 검증 | 무엇으로 확인했나 |
| 특이사항 | 막힌 것, 우회한 것. 없으면 생략 |

**2. 계획 외 개선** — 요청 건마다 한 항목

| 필드 | 담는 것 |
| --- | --- |
| 요청 | 사람이 무엇을 요구했나 |
| 조치 | 무엇을 바꿨나 |
| 결과 | 어떻게 됐나 |
| 검증 | 무엇으로 확인했나 |

**2번이 이 문서가 있어야 하는 이유다.** backlog에 없는 작업이므로 여기 적지 않으면
어디에도 남지 않는다. 그리고 이 구간이 다음 버전 `BRIEF`의 재료가 된다.

**담지 않는 것** — 계획(`PLAN`·`backlog`), 설계 결정(`DECISIONS`).

## 9. README.md

**이 프로젝트를 밖에서 처음 보는 사람에게 소개하는 공식 문서.** 6종에 속하지 않는다.
프로젝트 층이고 루트에 있으며 history로 가지 않는다.

**[llm-labs]** 이 절의 README는 **연습 폴더**의 `README.md`다. 개요는 저장소 `docs/INTENT.md`와
그 연습의 플랜(`docs/refs/`)을 참고해 초안을 쓴다.

INTENT가 생기기 전 이 자리는 "프로젝트가 무엇인가"의 SSOT를 겸했지만, 이제 그
역할은 `INTENT.md`가 가진다. README는 **GitHub 공개 레포의 관례를 따르는 소개
문서**로만 둔다 — 개요·설치·사용법.

| # | 블럭 | 필수 | 언제 쓰나 | 누가 |
| --- | --- | --- | --- | --- |
| 1 | 개요 | O | 착수 전 | 사람 (에이전트는 INTENT를 참고해 초안) |
| 2 | 설치 | 마감 후 | 버전 마감마다 갱신 | 에이전트 + 사람 승인 |
| 3 | 사용법 | 마감 후 | 버전 마감마다 갱신 | 에이전트 + 사람 승인 |
| 4 | 요구 환경 | 마감 후 | 런타임·의존 도구 | 에이전트 + 사람 승인 |

- **1. 개요** — 이 프로젝트가 무엇을 하는지 한두 문단. 판정 기준이 아니라 소개다.
  판정 기준(정체성)은 `INTENT.md`에 있다. 개요는 INTENT를 밖으로 풀어 쓴 것이며,
  INTENT와 어긋나면 안 된다.
- **2·3·4** — 착수 시점에 쓰지 않는다. 실제로 동작하는 것만 마감 때 적는다. `SPEC`에
  있었지만 안 된 것은 적지 않는다. 사용법은 결과의 기록이다.

라이선스·기여 안내 같은 공개 레포 관례 블럭은 필요하면 더 둔다.

**담지 않는 것** — 이번 버전 요구·설계·진행(그건 `docs/current/`가 담는다), 프로젝트
정체성의 원천(그건 `INTENT.md`).
